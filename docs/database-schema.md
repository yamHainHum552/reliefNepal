# Database schema plan

The database uses UUID primary keys, foreign keys, timestamps, constraints, indexes, and row-level security (RLS). Its current content tables are `profiles`, `programs`, `projects`, `project_impact_metrics`, `project_impact_details`, `board_members`, `gallery_items`, `network_partners`, `notices`, and `vacancies`. Every new gallery item must reference an existing project through `gallery_items.project_id`; project deletion is restricted while gallery items are attached. The project requirement is enforced for new rows while historical unassigned rows remain editable until they are linked and the constraint is validated. `newsletter_subscriptions` remains the active private submission table. `contact_inquiries` is retained for historical rows; the Contact page now emails through EmailJS and the admin workspace does not expose this table. `user_role`, `project_status`, and `publication_status` are shared enums. Public roles can read only published content, open vacancies, and verified project impact figures. Admins and editors manage content through authenticated API requests; profile administration and private submissions are admin-only.

Migration history: `20261012000000_initial_core.sql` creates profiles, programs, projects, submissions, enums, and initial RLS; `20261016000000_project_banners.sql` adds Cloudinary banner fields to projects; `20261017000000_admin_content_and_programs.sql` seeds the five program categories and creates gallery, network partner, and notice tables; `20261018000000_notice_photos.sql` adds Cloudinary photo fields to notices; `20261019000000_vacancies_and_youtube_videos.sql` creates the dedicated vacancy table and YouTube URL constraint; `20261020000000_negotiable_vacancies.sql` removes salary fields; `20261025000000_board_members.sql` creates the board-member directory; `20261025152542_fix_board_members_admin_policy.sql` corrects board editor/admin access; `20261026065258_add_project_detail_fields.sql` adds detailed project content and legacy impact JSON columns; `20261026120000_normalize_project_impact.sql` creates structured project impact tables and migration; `20261026130000_link_gallery_items_to_projects.sql` adds the project reference; `20261026140000_require_project_gallery.sql` requires project assignment for new gallery rows and restricts project deletion while media remains attached; and `20261026150000_partner_network_profiles.sql` adds unique partner slugs and profile content, maps legacy affiliations into the resource-provider category, and restricts categories to two values.

## Table inventory

| Area                  | Tables                                                                     | Purpose and access                                                                                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts and roles    | `profiles`                                                                 | One role-bearing profile per Supabase Auth user. Users can read their own profile; admins manage roles.                                                                                                  |
| Programs and delivery | `programs`, `projects`, `project_impact_metrics`, `project_impact_details` | Projects belong to a program and own repeatable impact rows. Public access is limited to published projects and verified metrics. Admins/editors manage content.                                         |
| Organization          | `board_members`                                                            | Ordered board directory; public reads active members, editors/admins manage entries.                                                                                                                     |
| Public communications | `gallery_items`, `network_partners`, `notices`                             | Published gallery media, partner profiles with exactly two categories, and notices. Draft content is hidden from public roles.                                                                        |
| Recruitment           | `vacancies`                                                                | Independent job records with job type/level, location, schedule, requirements, deadline, application details, and open/closed publication state. Salary is intentionally absent and shown as negotiable. |
| Private submissions   | `contact_inquiries`, `newsletter_subscriptions`                            | Newsletter subscriptions are active; contact rows are retained for history. RLS limits private data access.                                                                                              |

Relationships are enforced with foreign keys: impact rows cascade with their project; project program assignments become null if a program is deleted; profile rows cascade with their Auth user. Each managed public-content table uses the shared publication states where appropriate. RLS is enabled on all application tables; privileged management uses the authenticated user's profile role rather than a browser-held service key.

## Project impact content

`project_impact_metrics` stores one measurable outcome per row: label, displayed value, unit, reporting period, measurement date, source/evidence note, verification status, and display order. Values are text so existing formats such as `1,200+` and percentages remain intact. Metrics start as `unverified`; public RLS exposes only verified metrics for published projects. Editors and admins can review and verify them in the project editor.

`project_impact_details` stores one narrative result per row with a short title, description, and display order. Both impact tables cascade when their project is deleted and are editable through the `/admin` project form. The previous `projects.impact_numbers` and `projects.impact_details` JSONB columns are retained but deprecated for rollback; the migration copies valid array entries into the new tables and the application no longer writes to those columns.

Add the remaining entities as focused migrations when their workflows are designed:

| Entity                                 | Planned relationships and controls                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project locations                      | Project foreign key; district and municipality foreign keys; indexed geography codes.                                                                                           |
| Districts and municipalities           | Canonical geographic hierarchy, stable unique codes, and indexes.                                                                                                               |
| Organization-wide impact indicators    | Separate verified, source-backed figures for the homepage; project-specific figures already live in `project_impact_metrics`.                                                   |
| Stories and news posts                 | Optional project/program links; publication state, slug uniqueness, timestamps; public read for published records.                                                              |
| Partners                               | Implemented in `network_partners`: unique profile slug, category constrained to `local_district` or `resource_provider`, logo, descriptions, optional location/contact/collaboration details, and display order. Public roles read published profiles; editors/admins manage them. |
| Reports and financial documents        | Storage object reference, report period, type, publication status; no public access to drafts.                                                                                  |
| Media assets                           | Storage path, media type, alt text, licensing/consent metadata, publication status.                                                                                             |
| Contact and partnership inquiry review | Historical `contact_inquiries` rows remain protected by admin-only RLS, but the Contact page and admin workspace no longer read or write them.                                  |
| Newsletter unsubscribe workflow        | `newsletter_subscriptions` stores private address data and consent timestamp; only authenticated admins can select them. Add unsubscribe state and a verified unsubscribe flow. |
| Publication and audit logs             | Actor, action, entity, timestamp, structured change metadata; append-only administrative access.                                                                                |

Use one shared enum or constrained lookup table for publication status and user roles. Reporting periods should use explicit start/end dates and a documented period type. Administrative role assignment must be performed through a trusted server-side process; never allow users to self-assign elevated roles. Supabase service-role credentials belong only in backend secrets and bypass RLS, so use them sparingly and never in browser code.
